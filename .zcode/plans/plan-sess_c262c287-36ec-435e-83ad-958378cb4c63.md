
# GitHub Backend Auth & Copilot Phase 1 — Implementation Plan

## Overview

Move GitHub OAuth, repository operations, and Copilot auth from Electron/TypeScript into the Rust app-server via a new `providerAuth` protocol domain. The app-server becomes the sole backend for credentials; the desktop is a thin UI layer.

## Architecture

```
Desktop Renderer           Desktop Main (Electron)          Rust App-Server
─────────────────          ───────────────────────          ──────────────
GitSettings.tsx            rustAppServerAuthService.ts      providerAuth processor
  │                          │                                │
  ├─ startGithubLogin()  →  ├─ openConnection()             ├─ POST github.com/login/device/code
  │                          │  ├─ initialize()              ├─ store device_code + interval
  │                          │  ├─ startLogin(providerID)   │
  │                          │  └─ close()                   │
  │                          │                                │
  ├─ pollGithubLogin()   →  ├─ openConnection()             ├─ POST github.com/login/oauth/access_token
  │                          │  ├─ initialize()              ├─ on success: fetch user, encrypt token
  │                          │  ├─ pollLogin(providerID)    │  store in app-server config dir
  │                          │  └─ close()                   │
  │                          │                                │
  ├─ logoutGithub()      →  ├─ openConnection()             ├─ delete stored token
  │                          │  ├─ initialize()              │
  │                          │  ├─ logout(providerID)       │
  │                          │  └─ close()                   │
  │                          │                                │
  └─ listRepositories()  →  ├─ openConnection()             ├─ GET api.github.com/user/repos
                             │  ├─ initialize()              ├─ uses stored token from secure storage
                             │  ├─ listRepositories()       │  never returns token in response
                             │  └─ close()                   │
```

**1c. Provider auth processor: `app-server/src/request_processors/provider_auth_processor.rs`**

A new `ProviderAuthRequestProcessor` struct with:
- `state: Arc<ProviderAuthState>` — holds in-flight device-code attempts (by provider_id)
- `config_dir: PathBuf` — for token storage (app-server shared config dir)

Methods:
- `read_status(provider_id)` — reads token from encrypted file, returns auth status
- `start_login(provider_id, client_id)` — GitHub device-code start, stores attempt
- `poll_login(provider_id)` — checks stored attempt, polls GitHub, on success stores token
- `cancel_login(provider_id)` — cancels in-flight attempt
- `logout(provider_id)` — deletes stored token
- `list_repos(provider_id)` — calls GitHub API with stored token
- `clone_repo(repo_url, local_path)` — clones via git with temporary credential helper

Token storage: encrypted JSON files in `{config_dir}/provider-auth/{provider_id}.json`
- Encryption: use existing `safeStorage` equivalent via OS keyring or AES-GCM with derived key

**1d. Wire processor in `message_processor.rs`:**

Add `provider_auth_processor: ProviderAuthRequestProcessor` field, initialize in `new()`, add match arms in `handle_initialized_client_request()`.

**1e. Copilot auth (Phase 1 scope):**

Copilot's device-code flow is similar to GitHub's but uses different endpoints:
- POST `https://github.com/login/device/code` with `client_id: "Iv1.b507a97c6c0a9f1b"` (Copilot's public client ID)
- POST `https://github.com/login/oauth/access_token` to poll
- Then POST `https://api.github.com/copilot_internal/v2/token` with the GitHub token to get Copilot token
- Copilot token refresh via the same endpoint

The Copilot SDK flow:
1. Get GitHub access token (via device code)
2. Exchange for Copilot token at `https://api.github.com/copilot_internal/v2/token`
3. Use Copilot token in `Authorization: Bearer` header for model API calls

For Phase 1, implement as part of `providerAuth` with provider ID `github-copilot`. The Copilot token will be stored alongside the GitHub token.

### Phase 2: TypeScript Control Channel

**2a. Extend `RustAppServerControlService` (or create `RustAppServerAuthService`):**

New class `RustAppServerAuthService` following the same short-lived connection pattern:

```typescript
export class RustAppServerAuthService {
  async readStatus(providerID: string): Promise<ProviderAuthStatus>
  async startLogin(providerID: string, clientId?: string): Promise<DeviceCodeResponse>
  async pollLogin(providerID: string): Promise<ProviderAuthPollResponse>
  async cancelLogin(providerID: string): Promise<void>
  async logout(providerID: string): Promise<void>
  async listRepositories(providerID: string): Promise<ProviderRepoInfo[]>
  async cloneRepository(providerID: string, repoUrl: string, localPath: string): Promise<void>
}
```

Each method: open short-lived stdio connection → initialize → send RPC → close.

**2b. Wire into IPC handlers:**

Replace existing `githubService.ts` and `copilotAuthService.ts` implementations with calls to `RustAppServerAuthService`. The IPC handlers remain mostly the same — only the implementation beneath changes.

**2c. Update `DesktopApi` interface (if needed):**

The existing `DesktopApi` methods (`getGithubAuthStatus`, `startGithubLogin`, etc.) remain unchanged — the renderer doesn't need to know the backend changed. Only the main process implementation changes.

## Key Design Decisions

1. **Short-lived connections for auth**: Each auth RPC call opens a fresh stdio connection to the app-server. The app-server stores in-flight device-code attempts in memory (keyed by `provider_id`). This avoids maintaining a persistent connection.

2. **Token isolation by provider**: Each provider ID (`github-repositories`, `github-copilot`) has its own encrypted token file. This allows independent login/logout per service.

3. **Tokens never in RPC responses**: The app-server uses stored tokens for API calls but `readStatus` and `pollLogin` responses only contain `authenticated: true/false` and basic user info — never the token.

4. **Git clone via app-server**: The app-server uses `gix` or `git2` with a temporary in-process credential helper. The clone happens server-side; the desktop only specifies the target directory.

5. **Copilot as model provider**: The Copilot token is stored by `github-copilot` provider. The model provider selection checks `providerAuth/readStatus` for `github-copilot` — if authenticated, Copilot models appear in the model picker.

6. **Phase 1 boundaries**: No GitHub Enterprise. No `openai/form` MCP changes. No OAuth PKCE flow. Device-code only. Users still provide their own GitHub OAuth Client ID.
